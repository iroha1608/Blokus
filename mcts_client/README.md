# mcts_client — 理論解説

このパッケージが採用しているのは **Policy-guided Monte Carlo Tree Search (Policy-MCTS / UCT)**、すなわち「ゲーム木をモンテカルロ的にサンプリングしながら、訪問回数で最良手を決める」探索アルゴリズムである。本ドキュメントは初学者向けに、

1. なぜ MCTS なのか（背景理論）
2. MCTS の 4 フェーズが**それぞれ何のために存在するか**
3. 本実装がどの式・どの定数で動いているか
4. なぜそのチューニングなのか

を一気通貫で説明する。読み終えた時点で、`search.py` のコードを 1 行ずつ追えるようになるのが到達点。

---

## 0. 前提となる問題設定

Blokus Duo は次の性質を持つ **二人零和・完全情報ゲーム**:

- 盤面 14×14 = 196 セル
- 双方 21 種類のピース（1〜5 マス）を 1 個ずつ持つ
- 自分の置いたピースに **角（斜め）でだけ接する** ように新しいピースを置く
- 辺（直交）で接してはいけない
- 置けなくなったらパス
- 双方終了時、**盤上に置けたマス数の合計** が高い方の勝ち

特徴は

- **分岐数が異常に大きい**：初手で 100 通り超、中盤は 1 ピース × 8 回転 × 数十通りの角接続セルで簡単に 1000+ 候補
- **局面評価が難しい**：「あと何手伸びるか」という幾何学的なリーチが効くので、単純に置きマス差だけでは弱い
- **時間制限が厳しい**：サーバ側 1 手 10 秒タイムアウト

→ 全探索（minimax / α-β）は深さ 3〜4 でも厳しく、しかも評価関数の精度が出ないと α-β は壊れやすい。
**ヒューリスティック評価＋少数サンプル＋反復改善** で逐次最良手に近づく MCTS が相性が良い、というのが採用根拠。

## 1. MCTS の全体像

MCTS は次の 4 フェーズを **1 シミュレーション** として、制限時間内で何千回も繰り返すアルゴリズム。

```
        ┌─────────────────────────────────────┐
        │  ルートから「未展開手が残る葉」まで │
   1.   │  UCT で経路選択 (Selection)         │
        └─────────────────┬───────────────────┘
                          │
        ┌─────────────────▼───────────────────┐
        │  葉の未展開手から 1 つを取り出して  │
   2.   │  新ノードを生やす (Expansion)       │
        └─────────────────┬───────────────────┘
                          │
        ┌─────────────────▼───────────────────┐
        │  新ノードからランダム or 軽い方策で │
   3.   │  数手プレイアウト (Rollout)         │
        │  終局推定値 v を得る                │
        └─────────────────┬───────────────────┘
                          │
        ┌─────────────────▼───────────────────┐
        │  ルートまで visits++, ΣV += v       │
   4.   │  を加算 (Backpropagation)           │
        └─────────────────────────────────────┘
```

時間切れになったら、**ルート直下の子のうち最も訪問回数の多いもの** の手を返す。
「訪問回数最大 ≒ 最も真剣に検討された手 ≒ 最良手」というのが UCT の収束則による。
（値の平均 Q を直接使わない理由：終盤の少サンプル子の Q が偶然高く出るのを避けるため。「みんなが見てる手」のほうが信頼できる）

## 2. ノード設計

`search.py` の `Node` クラスが保持する情報:

| フィールド | 意味 | なぜ持つ必要があるか |
|---|---|---|
| `own`, `opp` | 自分・相手の占有を表す **196 ビット整数** | 局面を完全に表す。コピーを最小化 |
| `my_usable`, `opp_usable` | 未使用ピース集合 `frozenset[str]` | どのピースを置けるかを動的に管理 |
| `my_first`, `opp_first` | 「まだ初手前か」フラグ | 初手は中央 4 セルを覆う必要がある特殊ルール |
| `my_turn` | このノードでどちらが指す番か | Selection 時の符号反転に使う |
| `parent`, `parent_move` | 親ノードと、親→自分への遷移手 | Backpropagation で根まで遡るため |
| `children` | 展開済み子ノード | 木構造そのもの |
| `visits`, `value_sum` | 累積訪問数 / 累積評価値 | UCT 統計の本体 |
| `prior` | この子に対するポリシー由来の事前確率 | PUCT 式で探索を歪めるため |
| `untried_moves` | まだ展開していない候補手のリスト | Expansion で 1 個ずつ pop していく |

ポイントは **盤面コピーをしない設計** であること。子ノードを作るときは `own | mv.mask` のように整数 OR で派生状態を 1 つ作るだけで、過去ノードに副作用が無い。
Python の int は任意精度なので、196 ビット盤面が **1 つの数** として扱える。

## 3. フェーズ 1: Selection（UCT 経路探索）

ルートから「もう展開し切ったノード」を辿り、「まだ未展開の手があるノード（葉）」に到達するまで降りていく。
このとき**どの子を辿るか**を決める式が、本実装の核となる **PUCT (UCB1 の方策付き亜種)**:

```
score(child) = ±Q(child) + C_PUCT * prior(child) * sqrt(parent.visits + 1) / (1 + child.visits)
```

ここで:

- `Q(child) = child.value_sum / child.visits` ：子の平均評価値（自分視点）
- 第 1 項の符号は **`parent.my_turn ? +1 : -1`**（自分の手番では Q が高い手を選び、相手の手番では Q が低い手を選ぶ＝相手の最悪手を読む）
- 第 2 項は「**まだあまり訪問されていない / 事前評価が高い** 子をボーナス」する**探索項 (U)**
- `C_PUCT = 1.4`：探索 vs 活用のバランス。大きいほど未踏ノードへ寄る

これが「UCB1 で多腕バンディット問題を最適に解く」枠組みの拡張版で、AlphaGo Zero でも使われた式。

#### 直観

- 「Q」は「ここまでで分かった**実力**」
- 「U」は「**まだ十分試してない手にもチャンスを**」というブースト
- 両方足して比較することで、**良さそうな手を集中的に深掘り**しつつ **未知の手も拾える**

`search.py` 内では `_select()` が

```python
while node.children and (node.untried_moves is not None and not node.untried_moves):
    node = max(node.children, key=...)
```

と「展開しきった内部ノードでは降りる、それ以外（葉 or 未展開残り）では止まる」という条件で再帰的に降りる。

## 4. フェーズ 2: Expansion（木を 1 ノードだけ広げる）

Selection で到達した葉に未展開の手があれば、**先頭を 1 つだけ取り出して** 新しい子ノードを作る。
ここで「すべて展開する」のではなく **逐次 1 個ずつ展開する** ことで、探索のたびに木がほどよく広がる。

### 4.1 候補手の生成

合法手の列挙は `core/moves.py` で行う:

- **初手**：`generate_first_moves(side, usable)` — 中央 4 セル（`FIRST_TARGET_BIT[player]`）を覆う配置のみ
- **2手目以降**：`generate_moves(own, occupied, usable)`
  - **角接続セル** (`corner_attach_mask`) を計算：自分の駒に**斜め接する空セル** から **直交接するセル** を除いた集合
  - 各角接続セルを **アンカー** にして、事前展開された `PLACEMENTS_BY_ANCHOR[piece][cell]` テーブルを引く
  - 占有セル (`occupied`) と辺接触 (`side`) を共に避けるものだけ残す

ビット演算で `corner = empty & diag_neighbours(own) & ~ortho_neighbours(own)` のように 1 行で角接続セルが取れる（`bitboard.py:77`）のが速度の鍵。

### 4.2 ポリシースコアによる絞り込み

候補手が数百あっても、強い手の候補は通常 **2〜3 ダース以内**。
全部展開せず、**ポリシースコア上位 24 手のみ** に絞る (`TOP_K_EXPAND = 24`)。

```python
def _policy_score(p: Placement, opp_corner: int) -> float:
    return p.size * 4.0 + popcount(p.mask & opp_corner) * 2.0
```

意味:

| 項 | 効果 |
|---|---|
| `p.size * 4.0` | **大きいピースを優先**。Blokus Duo は残りピース＝マイナス点なので、大ピースを早く出さないと損 |
| `popcount(p.mask & opp_corner) * 2.0` | **相手の角接続セルを潰す手にボーナス**。相手の伸びる場所を直接消す＝攻撃的に有利 |

このスコアは

- 展開順序（`untried_moves.pop(0)` で先頭から）
- PUCT の `prior` の値（高スコアの手ほど U 項がブーストされる）

の両方に使われる。**「ありそうな手」から優先的に伸ばすことで、限られたシミュレーション回数で深さを稼ぐ**戦略。

### 4.3 状態遷移

`_child_state(node, mv)` で新ノードを作る。自分手番なら:

```python
new_own = node.own | mv.mask          # mv のビットを自分占有に追加
new_my_usable = node.my_usable - {mv.name}  # 駒を消費
# 新ノードは my_turn=False（相手の番）に切り替わる
```

相手手番なら `opp` 側を同様に更新する。
`frozenset - {...}` で `frozenset` 同士を作るため、親ノードの `my_usable` は不変。

## 5. フェーズ 3: Rollout（軽量ランダムプレイアウト）

展開した新ノードから **12 手だけ進めて** 簡易評価値を取る (`ROLLOUT_DEPTH = 12`)。

### 5.1 なぜ「終局まで」やらないのか

純粋な MCTS なら終局までランダムに指して勝敗を返す。が、Blokus は

- 終局が浅くて 30〜40 手
- 完全ランダムプレイアウトの結果分散が大きい

ので、**「12 手進めた評価関数値」** のほうがシミュレーションごとの信号対雑音比が高い。
これは AlphaGo の「ロールアウト＋価値ネット」の延長線にある工夫で、本実装の評価関数 `evaluate()` が事実上「学習済み価値関数」の役割を果たす。

### 5.2 方策ありロールアウト

`_rollout()` の各手番:

```python
moves = generate_moves(...)
top = sorted(moves, key=lambda m: -_policy_score(m, opp_attach))[:4]
mv = random.choice(top)
```

**ポリシースコア上位 4 手から一様ランダムに選ぶ**。

これにより:

- **悪手連発による評価値の暴走を防ぐ**（純ランダムなら相手も自分も愚行を続けて意味のない局面になる）
- **微妙な揺らぎは残す**（決定論的にしてしまうと、同じ局面では常に同じ評価値しか得られず、MCTS の意味が消える）

「policy-bias 付き random.choice」が、計算コストと評価品質のトレードオフを取る要所。

### 5.3 ロールアウト末端での評価関数

12 手進めた最終局面で `evaluate(own, opp, my_usable, opp_usable)` を呼ぶ（`core/eval.py`）。

```
evaluate = w_score * (my_sq − opp_sq)            // 占有マス差
         + w_corner * (my_corner − opp_corner)   // 角接続セル数差
         + w_reach * reach                        // 窒息ペナルティ
         + w_territory * territory                // 2 歩リーチ領域差
         + bonus                                  // ピース全置きボーナス
```

各成分の意味:

| 成分 | 重み | 何を測っているか |
|---|---|---|
| `my_sq - opp_sq` | 1.0 | 「**今この瞬間の点差**」。最終勝敗そのもの |
| `my_corner - opp_corner` | 0.6 | 「**この先の手数の余地**」。角接続セルが多いほど、これから置ける場所も多い |
| `reach` | 2.0 | 角接続セルが 2 以下に減ったら `(3 - corner)^2` の指数ペナルティ。**自分の窒息は深刻に避け、相手の窒息は得点として加算** |
| `territory` | 0.25 | 自分の角接続セル → 直交・斜め隣接 → 空セル、を取って **「自分だけが届く領域 − 相手だけが届く領域」**。擬似ボロノイ |
| `bonus` | ±20 | 片方が全ピース置き切ったら ±20。終盤の極端な勝勢を反映 |

`reach` を二次関数にしているのは、角接続セル数 0〜2 と 3〜10 では「危機感」が桁違いに違うからで、**窒息間近の局面は他のヒューリスティックを無視してでも回避すべき**という強い信号を出すため。

このスカラー値 `v` がフェーズ 4 で逆伝播される。

## 6. フェーズ 4: Backpropagation（統計の更新）

ロールアウトで得た `v` を、葉ノードからルートまでの **すべての祖先ノード** に加算する:

```python
n = leaf
while n is not None:
    n.visits += 1
    n.value_sum += v
    n = n.parent
```

評価値 `v` は **自分（ルート手番のプレイヤー）視点** で計算されているので、相手手番のノードでも符号を反転せずそのまま加算してよい。
Selection 時に「相手手番ノードでは `-Q`」と符号反転するため、相手は **`v` を最小化する手** を選ぶように動く（minimax 的に正しい）。

`visits++` と `value_sum += v` の 2 つの更新だけで、

- `Q = value_sum / visits` ：その子を経由した試合の平均評価値
- `visits` ：その子の信頼度（試行回数）

が同時に保たれる。

## 7. 探索ループと終了判定

`Searcher.search()` の本体:

```python
while sims < 20_000 and time.monotonic() - start < time_budget * 0.9:
    leaf = _select(root)            # フェーズ1
    if leaf.untried_moves is None:
        leaf.untried_moves = _expand_untried(leaf, ...)
    if leaf.untried_moves:
        leaf = _expand(leaf, ...)   # フェーズ2
    value = _rollout(leaf, ...)     # フェーズ3
    _backup(leaf, value)            # フェーズ4
    sims += 1
```

終了条件:

- **`sims < 20000`**：上限。実際に 20000 まで届くのは終盤の浅い局面くらい
- **`time.monotonic() - start < time_budget * 0.9`**：時間制限。`time_budget` は `MCTS_BUDGET` 環境変数（デフォルト 8.0 秒）、サーバ側 10 秒タイムアウトに対して **0.9 倍のマージン** を取る

ループを抜けたら **ルート直下で訪問回数最大の子の手** を返す:

```python
best = max(root.children, key=lambda c: c.visits)
return best.parent_move, best.q()
```

訪問回数を基準にする理由は section 1 で触れた通り、Q（平均評価値）は試行数が少ない子で偶発的に高くなりうるが、訪問回数は「みんなが繰り返し検討した結果ここに収束した」という強い信号だから。

## 8. 相手手駒の自動推定

MCTS は相手の手番でも合法手を生成しないとシミュレーションが成立しない。
そこで毎ターン受け取る盤面文字列から、相手が**直前に何のピースを置いたか**を逆算する仕組みを `shared/client_base.py:_update_opp_usable()` に持つ。

```python
diff = opp_bb & ~self._prev_opp        # 新しく増えたビット
n = popcount(diff)                     # 増えたマス数 = ピースサイズ
candidates = [p for p in self._opp_usable if PIECE_SIZE[p] == n]
```

1. サイズ一致候補が **1 個ならそれが確定**
2. **複数候補**なら、各候補の事前展開された配置 `PLACEMENTS_BY_PIECE[name]` を順に試し、**ビットマスクが diff と完全一致** するピースを採用
3. ピース形状が回転して同型のときの曖昧性は、サイズ一致候補の先頭を仮選択（極稀ケース）

これで相手の `opp_usable` が常に正確に維持され、MCTS シミュレーション内で相手手番の合法手生成が正しく動く。

## 9. ビットボードによる高速化

すべての盤面演算が **Python int の OR / AND / シフト** で書かれている。これが MCTS の現実時間性能を支える。

主要プリミティブ (`core/bitboard.py`):

```python
shift_n(b) = b >> 14              # 北へ 1 段
shift_s(b) = (b << 14) & MASK     # 南
shift_w(b) = (b & NOT_COL_W) >> 1 # 西（左端を除外）
shift_e(b) = (b & NOT_COL_E) << 1 # 東
shift_nw / shift_ne / shift_sw / shift_se = それぞれの合成

ortho_neighbours(b) = shift_n(b) | shift_s(b) | shift_w(b) | shift_e(b)
diag_neighbours(b)  = shift_nw(b) | shift_ne(b) | shift_sw(b) | shift_se(b)

corner_attach_mask(own, occupied) =
    (BOARD_MASK & ~occupied)              # 空セル
    & diag_neighbours(own)                 # 自分に斜め隣接
    & ~ortho_neighbours(own)               # かつ直交隣接でない

side_touch_mask(own) = ortho_neighbours(own)  # 配置不可セル
```

`corner_attach_mask` は「自分の角接続セル＝次に置ける起点」を 1 行で出す中核演算。
これがなければ MCTS は分岐の列挙コストで死ぬ。

`PLACEMENTS_BY_PIECE[name]` / `PLACEMENTS_BY_ANCHOR[name][cell]` は `core/shapes.py` で**起動時に全 21 ピース × 8 回転 を事前展開**しているため、合法手生成は「テーブル引き + ビット AND」だけで終わる。

## 10. ハイパーパラメータと挙動への影響

| 定数 | 場所 | 既定値 | 大きくしたとき | 小さくしたとき |
|---|---|---|---|---|
| `C_PUCT` | `search.py:21` | 1.4 | 未探索の手にも積極的に行く（exploration↑） | 高 Q 手を集中的に深掘り（exploitation↑） |
| `ROLLOUT_DEPTH` | `search.py:22` | 12 | 評価が安定する代わりに 1 シミュが重くなる | 1 シミュが速くなる代わりに評価ノイズ↑ |
| `TOP_K_EXPAND` | `search.py:23` | 24 | 木が横に広がる（網羅性↑、深さ↓） | 木が縦に伸びる（深さ↑、見落とし↑） |
| `MCTS_BUDGET` | env var | 8.0 秒 | シミュ数↑で精度向上 | 探索品質低下 |
| `evaluate` の `w_*` | `core/eval.py:21` | 1.0/0.6/2.0/0.25 | 各成分の影響度を変えると指向性が変わる | 同上 |

「シミュ数」は実測で 1 手あたり **数百〜数千回**。終盤の浅い局面ほど多く、序盤の広い局面ほど少なくなる。

## 11. アーキテクチャ分離

通信ループとアルゴリズムが分離されている:

```
[ websocket サーバ ]
        │ 盤面の文字列
        ▼
┌─────────────────────────┐
│ BaseClient              │  ←── shared/client_base.py
│  parse_board()          │      ボード文字列 → ビットボード
│  _update_opp_usable()   │      相手手駒推定
│  _compute_action()      │      時間計測・パス処理
└──────────┬──────────────┘
           │ own, opp, first_move
           ▼
┌─────────────────────────┐
│ PlayerClient            │  ←── mcts_client/PlayerClient.py
│  choose_action()        │      Searcher を呼ぶだけ
└──────────┬──────────────┘
           │
           ▼
┌─────────────────────────┐
│ Searcher (MCTS)         │  ←── mcts_client/search.py
│  search()               │      上記 4 フェーズを回す
└─────────────────────────┘
```

別の探索アルゴリズム（純 α-β、policy net、heuristic search …）を試したいときは
`PlayerClient.choose_action()` だけ差し替えれば良い。
**通信プロトコル / 盤面パース / 相手手駒推定 は完全に再利用可能**。

## 12. 「なぜ MCTS が α-β より相性が良いか」の理論的根拠

短くまとめると 3 点:

### (a) 評価関数の不完全性に強い

α-β は **最善応手列の末端評価** が真値からズレているとそのまま結論を誤る。
MCTS は **多数のサンプル平均** を取るので、評価関数の偏り（バイアス）はある程度キャンセルされる。

### (b) 分岐爆発に対するソフトな枝刈り

α-β は深さ枝刈りで Y 軸に犠牲を払う。
MCTS の `TOP_K_EXPAND` + ポリシー prior は、**「広さを諦めて深さに振る」かどうかを統計的に自律調整** する。
強い手はもっと深く読まれ、弱い手は早々に放置される — これが自然と起きる。

### (c) いつ止めても答えが出る (anytime algorithm)

MCTS はループ 1 回ごとに「現時点での最良手」が更新可能で、時間制限が動的でも安全。
α-β の iterative-deepening でも近いことはできるが、深さ N と N+1 の評価値の連続性が崩れることがある。
MCTS は **訪問回数という単調統計** で最良手を出すので、その種の不連続が起きにくい。

## 13. 1 シミュレーションのトレース（具体例）

中盤局面で MCTS の 1 シミュが何をしているか:

```
ルート(my_turn=T, visits=523)
 ├─ child A: place "P5_rot2 @ (3,4)" prior=22, visits=312, Q=+4.2
 ├─ child B: place "L4_rot0 @ (7,8)" prior=18, visits=104, Q=+3.1
 ├─ child C: place "T4_rot1 @ (5,2)" prior=16, visits=58,  Q=+5.7  ← Q 高だが visits 少
 └─ child D: place "I3_rot0 @ (9,9)" prior=10, visits=49,  Q=+1.0
```

1. **Selection**：PUCT スコア計算
   - A: `+4.2 + 1.4 * 22 * sqrt(524)/313 ≈ 4.2 + 2.27 ≈ 6.47`
   - B: `+3.1 + 1.4 * 18 * sqrt(524)/105 ≈ 3.1 + 5.52 ≈ 8.62`
   - C: `+5.7 + 1.4 * 16 * sqrt(524)/59 ≈ 5.7 + 8.71 ≈ 14.41` ←選ばれる
   - D: `+1.0 + 1.4 * 10 * sqrt(524)/50 ≈ 1.0 + 6.43 ≈ 7.43`

   C はサンプルが少ない（exploration 項が大きい）＋ Q も高い → 選択

2. **Expansion**：C の `untried_moves` から先頭の手を 1 つ取り出して孫ノード C1 を生成

3. **Rollout**：C1 から 12 手、ポリシー上位 4 手ランダムで進めて `evaluate()` を計算 → `v = +6.3`

4. **Backpropagation**：
   - C1: visits 0→1, value_sum 0→6.3
   - C : visits 58→59, value_sum 330.6→336.9（Q = +5.71）
   - root: visits 523→524, value_sum +XXXX

次の Selection では C の visits が増えたぶん exploration 項が下がり、相対的に他の候補が上がる。
これを 数千回繰り返すと、**強い手は visits が雪だるま式に伸び**、弱い手は数十回で見限られる。

## 14. まとめ — 一文で

> Blokus Duo の巨大な分岐をビットボード演算で高速に列挙し、ポリシーで上位手だけ展開して PUCT で深掘りを偏らせながら、12 手の方策ありロールアウト末端で「占有差・角接続差・窒息度・領域差」の合成評価値を取り、訪問回数最大の手を返す — それが mcts_client。
